# ADR-0002：知识沉淀纵向闭环

- 状态：已接受
- 日期：2026-08-25

## 决策点

如何在不允许智能体自由修改正式能力的前提下，把一次成功运行转化为后续任务可复用、可审计、可回滚的知识资产。

## 候选方案

### A. 运行成功后直接写入长期记忆

实现最简单、复用延迟最低，但无法阻止幻觉、偶然经验和恶意输入污染正式知识库，也缺少评测、审批和回滚边界。

### B. 模块化单体内的受控应用服务闭环

运行事件先持久化，成功结果只生成成长候选；候选经过指纹去重、证据评测和显式审批后，才以事务发布为正式记忆。运行时只检索正式资产，回滚同步停用记忆。

### C. 第一版即采用事件总线和独立反思 Worker

能够独立扩容并隔离模型反思负载，但会提前引入消息投递、重试、幂等、死信和跨服务一致性成本。

## 决策

选择方案 B，并通过协议保留未来迁移到方案 C 的边界。

## 选择理由

- 满足“评测、审批、审计、版本和回滚”这一不可放宽的成长治理要求。
- PostgreSQL 事务能够保证候选激活、审批记录和正式记忆发布的一致性。
- `KnowledgeExtractor`、`CandidateEvaluator` 和 `KnowledgeAssetPublisher` 均为可替换协议，后续可以接入模型反思器、回归评测器和异步 Worker。
- 当前规模没有证据需要独立服务，模块化单体更容易验证端到端正确性。

## 反选论证

- 不选方案 A：任何自动提取错误都会立即进入运行上下文，风险不可接受。
- 暂不选方案 C：当前没有独立吞吐或团队边界，消息系统会扩大故障面，并延迟最小闭环交付。

## 接受的代价

- 当时默认提取器只处理成功输出；该限制已由 ADR-0003 的完整轨迹反思部分解决。
- 指纹存在 JSON 字段中，候选量很大时需要新增独立列和索引。
- 反思当前跟随应用服务执行；后续接入耗时模型时应转为 PostgreSQL Outbox + Worker。
- 当前发布目标只有正式记忆，技能、策略、工作流和领域能力包发布器尚未实现。

## 撤销条件

- 反思耗时或吞吐实测影响在线任务尾延迟。
- 需要独立扩缩容、失败重试、死信处理或跨部署消费运行事件。
- 单租户候选规模使 JSON 指纹扫描无法满足查询指标。

## 验证

- 单元测试验证未审批不可召回、重复输出不重复建候选、失败运行不学习以及回滚停用。
- PostgreSQL 集成测试验证运行与顺序事件落库、评测和审批审计、发布后下一次召回、回滚后停止召回。
- Ruff、Mypy、Pytest 和 Alembic drift check 必须全部通过。
