# ADR-0003：完整轨迹受控反思

- 状态：已接受
- 日期：2026-08-25

## 决策点

如何让模型从完整运行轨迹中提取事实、流程和失败教训，同时阻止秘密泄漏、提示注入、
伪造证据和未经审批的自动学习。

## 候选方案

### A. 只反思最终输出

实现简单，但看不到工具调用、失败、验证过程和中间修正，无法形成可靠失败记忆。

### B. 直接把原始事件数组交给反思模型

上下文完整，但可能泄漏凭证、超过模型容量，并让工具输出中的恶意指令污染反思。

### C. 完整轨迹加载后经过安全边界再做结构化反思

数据库加载完整顺序轨迹；发送模型前递归脱敏、限制单事件和总容量，并明确把轨迹视为
不可信数据。模型只允许返回严格 JSON，每项必须引用实际呈现的事件 ID。

## 决策

选择方案 C。继续复用不可变 `run_events` 作为事实来源，并把反思理由、证据事件 ID、
标签、适用范围、引擎和 Prompt 版本写入成长候选，不新增反思表。

## 选择理由

- 能覆盖模型正文、工具调用与结果、验证和失败，而不是只看最终答案。
- 脱敏与容量控制在模型调用前完成，提示注入内容被隔离为证据数据。
- 事件 ID 必须属于实际发送给模型的轨迹范围，裁剪掉的事件也不能被引用。
- 结构化输出通过 Pydantic 严格校验，非法 JSON、额外字段和缺失证据都会失败关闭。
- 反思结果仍经过指纹去重、评测、人工审批、事务发布和回滚，不扩大成长权限。

## 反选论证

- 不选 A：无法解释工具结果和失败根因，不能满足完整轨迹反思目标。
- 不选 B：原始轨迹可能包含秘密、超大输出和提示注入，生产风险不可接受。
- 暂不新增反思表：当前审计查询可由运行事件和候选 JSON 完成，专表会重复事实并增加一致性成本。

## 接受的代价

- 容量裁剪时只向模型呈现部分事件；被省略事件不能作为本次候选证据。
- 反思目前同步跟随应用服务执行，会增加任务完成后的尾延迟。
- 当前只发布记忆资产，技能、策略和领域能力包发布器仍待实现。

## 撤销条件

- 反思吞吐或尾延迟需要独立扩缩容、重试、死信和消费进度管理。
- 审计、统计或合规查询证明候选 JSON 无法满足反思记录的独立检索需求。
- 轨迹容量策略在真实负载下持续丢失关键证据，需要摘要层或分段反思协议。

## 验证

- 单元测试覆盖成功与失败反思、秘密脱敏、提示注入、容量裁剪、非法 JSON、缺失/伪造/
  范围外证据和响应内去重。
- PostgreSQL 集成测试覆盖模型、工具、验证和终态事件的顺序加载，以及真实事件证据回查。
- 失败记忆只到 `awaiting_approval`，未审批时正式记忆检索为空。
