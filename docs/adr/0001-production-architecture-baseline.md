# ADR-0001：生产级架构基线

- 状态：已接受
- 日期：2026-08-25

## 决策点

通用智能体框架应采用怎样的默认运行、存储和成长架构，才能同时支持专业化、持续成长和生产部署。

## 候选方案

### A. 本地优先的轻量单体

- SQLite 存储。
- 单进程运行。
- 记忆直接写入。
- 不提供统一审批、版本和回滚。

优点是启动简单；缺点是并发、审计、权限和成长治理不足，后期迁移成本高。

### B. 生产级模块化单体

- Python 异步运行内核。
- PostgreSQL + pgvector 作为主存储。
- Redis 用于缓存、短期状态和后台任务协作。
- 运行与成长双循环。
- 领域能力包、评测、审批、版本和回滚从第一版纳入模型。

优点是边界清晰、可演进并满足生产治理；代价是初始工程量和基础设施要求更高。

### C. 从第一版开始拆分微服务

- 运行、记忆、工具、训练、评测、治理分别部署。

优点是独立扩展；缺点是部署、调试、事务、版本协作和运维复杂度过高，不适合项目初期。

## 决策

选择方案 B：生产级模块化单体。

## 选择理由

- 符合项目“通用内核 + 领域能力包 + 受控成长”的核心目标。
- PostgreSQL 能同时承担事务、JSON、全文检索和向量检索。
- 模块化边界允许未来按压力和组织边界拆分服务。
- 从第一版保留审计、审批和回滚，避免自我成长变成不可控自我修改。

## 反选论证

- 不选方案 A：无法满足多租户、并发、权限、审计和可靠成长要求，后续重构会触及所有数据模型。
- 不选方案 C：当前没有独立扩容和团队边界证据，微服务会引入分布式一致性和运维成本。

## 接受的代价

- 本地开发需要 Docker、PostgreSQL 和 Redis。
- 需要维护数据库迁移、连接池、备份和恢复流程。
- 初始模块设计和测试成本高于轻量原型。

## 撤销条件

- 单体部署已经通过性能实测确认无法满足吞吐或隔离要求。
- 某个模块出现独立扩容、独立合规或独立团队维护需求。
- pgvector 在目标数据量和查询模式下经基准测试无法满足检索指标。

## 验证

- 单元测试验证领域包、运行循环、审批和成长状态机。
- PostgreSQL 集成测试验证事务、约束、迁移和向量字段。
- 压测验证运行事件写入、记忆检索和并发任务处理能力。
- 回归评测验证能力升级不会降低已有专业能力。
